# JopaQuizProject

Personal quiz application. It serves multiple-choice questions (4 options, exactly one correct), tracks the score (right/wrong), and for each question references the part of the source document where the answer is found.

Questions are generated by Claude from documents the user provides, via a dedicated Claude skill (planned: `.claude/skills/generate-quiz/`).

## Constraints

- Not published to any app store. Used by the owner and shared with a few other people on their own devices.
- Must run on **Windows** and **Android**.
- The user works in **JavaScript / TypeScript**.

## Status of key decisions

| Topic | Decision |
|---|---|
| Tech stack | PWA — React + TypeScript + Vite, `vite-plugin-pwa` (manifest, service worker, offline use) |
| Hosting | GitHub Pages from the **public** repo `M-E-7/JopaQuizProject`, deployed by GitHub Actions → https://m-e-7.github.io/JopaQuizProject/ |
| Local storage | IndexedDB; request `navigator.storage.persist()` to reduce eviction |
| Sync between devices | None — scores and imported quizzes are per device |
| Question file format | JSON, format v1 — `schema/quiz-set.schema.json`, documented in `schema/README.md` |
| Quiz set ↔ documents | A set can combine several source documents; each question names its `sourceId` |
| Explanation | Required on every question (1–2 sentences) |
| Optional question metadata | `tags` only (no difficulty) |
| Source document formats | .docx and .csv for now; ingestion must be extensible to other formats |
| Question language | Same language as the source document |
| Source reference display | Location + quoted passage shown inside the app (the original document is not opened) |
| Getting quizzes onto devices | Import a quiz JSON file at runtime via a file picker (no rebuild/redeploy needed) |
| Score persistence | Local history per quiz set (date, right, wrong, missed question ids) |

## Privacy / public repo

- The GitHub repo is public. **Never commit anything from `documents/` or `quizzes/`** — both are gitignored.
- Quiz JSON files are transferred to devices manually and imported in the app; they are never part of the deployed site.

## Architecture rule

- File import and storage go through a small platform interface (e.g. `QuizStorage`, file-import helper). UI code must not call IndexedDB or file APIs directly, so the app can later be wrapped (Tauri / Capacitor) without a rewrite.

## Installing on devices

- **Windows:** open https://m-e-7.github.io/JopaQuizProject/ in Edge (address-bar "App available" icon, or ⋯ → Apps → Install this site as an app) or Chrome (install icon, or ⋮ → Cast, save, and share → Install page as app).
- **Android:** open the URL in Chrome → ⋮ → "Install app" / "Add to Home screen".
- Clearing the site's data in the browser wipes that device's quizzes and score history — never suggest it as a fix.

## Updating the app

1. Claude changes `app/`, makes sure `npm run build` and `npm run lint` pass, and gives a commit message.
2. The user commits and pushes to `main`; the deploy workflow publishes it (~1–2 min, GitHub's CDN can serve old files for up to ~10 min).
3. Installed apps update themselves, but it takes **two launches while online**: the first launch shows the old (cached) version and downloads the new one in the background; the next launch runs the new version.
   - Windows: close and reopen the app window, or F5 / Ctrl+R inside it. If stuck: Ctrl+Shift+R.
   - Android: fully close the app (swipe it away in recent apps) and reopen.
   - Home-screen name/icon changes can take up to ~a day on Android.
4. The planned "new version available → Reload" notice (Phase 4) and the version label (Phase 1) make this easier.

**Data compatibility rule:** imported quizzes and score history live in IndexedDB on each device and survive app updates. Any change to how data is stored must migrate existing data (bump the IndexedDB version and convert in the upgrade handler) — never drop or silently ignore a user's stored quizzes or history.

## Tooling

- Only Node is required to develop and build (Node 24 / npm 11 on the dev PC). No Android SDK or Rust needed.
- Only the owner's PC builds the project; other devices just run the hosted app.
- App stack versions (scaffolded with `create-vite` 9): Vite 8, React 19, TypeScript 6, linting with **oxlint** (`app/.oxlintrc.json`, not ESLint).

## Commands

Run from `app/`:

```bash
npm install      # once, or after dependency changes
npm run dev      # dev server with hot reload (http://localhost:5173/JopaQuizProject/)
npm run build    # type-check (tsc -b) + production build into app/dist/
npm run preview  # serve the production build locally
npm run lint     # oxlint
npm run generate-pwa-assets  # regenerate PNG/ICO icons in public/ after editing public/favicon.svg
```

- `.claude/launch.json` defines `app-dev` (dev server, port 5173) and `app-preview` (production build, port 4173) for Claude's browser preview. Vite `base` is `/JopaQuizProject/` everywhere (dev, preview, production), so after starting either one navigate to `/JopaQuizProject/` — the bare origin returns 404. The service worker only runs in the production build, so test PWA/offline behaviour with `npm run build` + `app-preview`.

## Deploying

- `.github/workflows/deploy.yml` runs on every push to `main` that touches `app/**` or the workflow itself (or manually via "Run workflow" in the Actions tab).
- Steps: `npm ci` → `npm run lint` → `npm run build` → upload `app/dist` → deploy to GitHub Pages. A lint or type error stops the deploy.
- One-time repo setup (owner): Settings → Pages → Source: **GitHub Actions**.
- Changes to docs, `schema/` or task files don't trigger a deploy.
- How devices pick up a deploy: see "Updating the app" above.
- On Windows, stop the dev/preview server before `npm ci` — it locks files in `node_modules` and the install fails half-way.

## PWA setup

- `vite-plugin-pwa` (config in `app/vite.config.ts`): web manifest, Workbox service worker (`generateSW`) that precaches the whole app shell, so the app works fully offline.
- `registerType: 'autoUpdate'` with the plain `registerSW.js` script (no `virtual:pwa-register` import): the new service worker activates in the background, but the open page is not reloaded — hence the two-launch update. The Phase 4 "new version available" notice will need `'prompt'` and the `virtual:pwa-register` module instead.
- Icons: single source `app/public/favicon.svg` (four answer bars, one green with a check mark). `app/pwa-assets.config.ts` generates the PNG/ICO sizes; maskable and Apple icons use the brand blue `#2563eb` as background. Generated icons are committed.
- Theme: `app/src/index.css` defines colour tokens (`--text`, `--bg`, `--surface`, `--accent`, `--correct`, `--wrong`, …) for light and dark (`prefers-color-scheme`). Use the tokens, not hard-coded colours.

## Quiz file format

Full spec: `schema/README.md`. Key rules:

- Exactly 4 unique options, one `correctIndex` (0–3), required `explanation` and `reference` with a verbatim `quote`.
- Question ids `q0001`, `q0002`, … are stable: never renumber or reuse them (score history refers to them). Appended questions get the next free number.
- If the format changes, update the schema, `schema/README.md` and `schema/examples/example-quiz.json` together, and bump `formatVersion` for breaking changes.

## Source documents

- **.docx** — `location.type: "section"` with the heading path to the section, plus a verbatim quote of the passage containing the answer.
- **.csv** — content varies: may be a fact table (e.g. term/definition) or ready-made Q&A rows. `location.type: "row"` with the spreadsheet row number (header = row 1) and column names; quote as `Column: value | Column: value`.

## Repository layout

- `documents/` — source documents to generate questions from (**gitignored** except its README).
- `quizzes/` — generated quiz sets, `<quiz-id>.json` (**gitignored** except its README).
- `schema/` — quiz format schema, spec and committed example quiz.
- `app/` — the React PWA (Vite project: `src/`, `public/` icons, `vite.config.ts`, `pwa-assets.config.ts`).
- `.github/workflows/deploy.yml` — build + deploy to GitHub Pages.
- `.claude/launch.json` — dev/preview server configs for Claude's browser pane.
- `todo.md` — open tasks, grouped by phase, with a "Where we are" note at the top.
- `completedTasks.md` — finished tasks with completion date (newest first).

## Workflow rules for Claude

- **Never commit or push.** The user commits and pushes manually.
- "Let's go next task" means: take the first open task in `todo.md` (check the "Where we are" note first).
- After each completed task:
  1. Move it from `todo.md` to `completedTasks.md` (with the date and how it was verified) and refresh the "Where we are" note.
  2. Update this file if the task produced a decision, a new convention or new commands.
  3. Give the user a suggested git commit message in a code block.
- Before finishing a task that touches `app/`, run `npm run build` and `npm run lint` and make sure both pass; check UI changes in the browser pane (`app-dev`, or `app-preview` for PWA/offline).
- For significant decisions, discuss pros and cons and let the user choose (they like to understand trade-offs). Ask when something is unclear rather than guessing.
- When the user has to do something themselves (GitHub settings, installing on devices), give a short step-by-step guide.
- The app also runs on other people's devices — keep stored data compatible across updates (see "Updating the app").
